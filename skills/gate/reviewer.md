# kotlin-harness 리뷰어 지침

리뷰 스킬이 실행한 에이전트가 따르는 지침이다. 입력으로 아래 값을 받는다.

- 범위와 인자, 플러그인 경로, 설정(`platform`·`excludeCategories`·`autoFix`)
- 리포트 경로, 시작 커밋(리뷰 시작 시점의 `HEAD`), 작업 중인 파일(리뷰 시작 시점에 커밋되지 않은 변경이 있던 파일)

## 1. 대상 파일 수집 (`.kt`, `.kts` 만)

| 범위 | 명령 | 리뷰 대상 |
|---|---|---|
| `file <경로>` | — | 파일 전체 |
| `diff` | `git diff HEAD` + `git ls-files --others --exclude-standard` | 커밋되지 않은 변경 줄 |
| `branch [base]` | `git diff $(git merge-base <base> HEAD)` (base 기본값은 `git symbolic-ref --short refs/remotes/origin/HEAD` 의 브랜치, 없으면 `main`) | 브랜치에서 변경된 줄 |
| `pr [번호]` | `gh pr diff [번호]` (번호가 없으면 현재 브랜치의 PR) | PR 에서 변경된 줄 |
| `project` | `git ls-files '*.kt' '*.kts'` | 파일 전체 |

변경 줄이 대상인 범위에서는 변경되지 않은 기존 코드의 위반을 결과에서 제외한다.

## 2. 룰 로드

- `<플러그인 경로>/rules/common/**/*.md`
- `<플러그인 경로>/rules/<platform>/**/*.md` (platform 이 없으면 로드하지 않는다)

`excludeCategories` 에 적힌 카테고리 경로 아래의 룰은 로드하지 않는다. `common/` 과 `<platform>/` 양쪽에 적용한다 (예: `scope-functions` → `rules/common/scope-functions/`, `ui/view` → `rules/android/ui/view/`).

룰 ID 는 `rules/` 기준 상대 경로(확장자 제외)다 (예: `common/null-safety/safe-cast`). frontmatter 의 `applies_to` glob 에 해당하는 파일에만 적용하고, `## 허용` 섹션에 해당하는 코드는 위반으로 보고하지 않는다.

## 3. 위반 수정과 커밋

영향 판정은 `autoFix` 와 관계없이 모든 위반에 실행한다. `review.autoFix` 가 `false` 이면 영향 판정만 하고, 수정·커밋은 건너뛰어 소스 파일을 수정하지 않는다.

### 영향 판정

룰에 해당한다고 해서 현재 코드에서 문제가 발생한다는 뜻은 아니다. 위반마다 룰이 설명하는 문제가 현재 코드에서 실제로 발생하는지 판정해 리포트의 `영향` 에 근거와 함께 적는다.

| 영향 | 기준 | 예 |
|---|---|---|
| `실제 문제` | 현재 코드의 실행 경로에서 문제가 발생한다 | 이펙트가 캡처한 파라미터에, 호출하는 쪽이 리컴포지션마다 다른 람다를 전달한다 |
| `방어용` | 현재 코드에서는 동작이 바뀌지 않는다. 이후 코드가 바뀌면 문제가 될 수 있다 | 호출하는 쪽이 `remember` 로 만든 객체만 캡처한 같은 람다를 전달한다. `stringResource` 처럼 설정이 변경될 때만 바뀌는 값이고, 그때 Activity 가 다시 생성되어 이펙트도 다시 시작된다 |
| `판정 불가` | 판정에 필요한 코드가 리포 밖에 있거나, 실행 시점에만 알 수 있다 | 호출하는 쪽이 다른 리포의 모듈이다 |

- 값의 출처를 리포 안에서 확인한다. 파라미터면 호출부를 검색하고(`git grep`), 프로퍼티면 선언과 대입하는 곳을 확인한다.
- 확인하지 않고 `실제 문제` 로 판정하지 않는다. 확인할 수 없으면 `판정 불가` 로 적는다.
- `방어용` 이면 어떤 변경이 생기면 문제가 되는지 근거에 적는다.
- severity 는 룰의 값을 그대로 적는다. 영향 판정으로 severity 를 바꾸지 않는다.

### 수정 대상

- 룰의 `## 수정` 에 따라 수정 방법이 하나로 정해지는 위반만 수정한다.
- 아래 경우는 수정하지 않고, 리포트에 `수정하지 않음` 과 이유를 적는다.
  - 수정 방법이 여러 가지이고 어느 쪽이 맞는지 코드만으로 판정할 수 없는 경우 (예: `null` 일 때 기본값을 쓸지 예외를 발생시킬지)
  - 파일 밖의 호출부나 public API 시그니처를 함께 수정해야 하는 경우
- 위반과 관계없는 코드는 수정하지 않는다.

### 커밋

- git 리포가 아니거나, 입력의 `작업 중인 파일` 목록에 있는 파일이면 그 파일은 수정만 하고 커밋하지 않는다. 사용자의 작업 중인 변경이 함께 커밋되지 않게 하기 위해서다. 리포트에 이유를 적는다.
- 같은 이유로 수정한 변경을 커밋 하나로 묶는다. 같은 식에서 나온 위반 여러 건은 이유가 달라도 커밋 하나로 묶는다. 영향이 다른 수정(`실제 문제` 와 `방어용`)은 한 커밋에 섞지 않는다. 커밋할 파일은 `git add <경로>` 로 하나씩 지정하고, `git add -A`·`git add .` 는 사용하지 않는다.
- 리포트 파일은 커밋하지 않는다. 푸시하지 않는다.

### 커밋 메시지

룰을 모르는 사람도 무엇을 왜 수정했는지 알 수 있게 평문으로 적는다. 언어와 형식은 프로젝트의 기존 커밋 메시지를 따른다.

- 제목: 어떤 코드를 어떻게 수정했는지
- 본문: 영향 판정에 따른 설명, 수정한 파일
  - `실제 문제`: 어떤 조건에서 어떤 문제가 발생하는지
  - `방어용`: 현재 동작은 바뀌지 않는다고 적고, 어떤 변경이 생기면 문제가 되는지 적는다. 문제가 발생했던 것처럼 서술하지 않는다.
  - `판정 불가`: `~하면 ~할 수 있다` 처럼 조건을 함께 적는다. 조건 없이 단정하지 않는다.
- 타입 접두사: 프로젝트가 `fix:`·`refactor:` 같은 접두사를 쓰면 `fix` 는 `실제 문제` 를 수정한 커밋에만 쓴다. `방어용` 은 `refactor` 처럼 프로젝트가 동작이 바뀌지 않는 수정에 쓰는 타입을 쓴다.
- 금지: 룰 ID·카테고리 이름, `룰 위반`·`N번째 룰` 같은 표현, 줄 번호 나열, `kotlin-harness` 등 도구 이름

```
# 금지
fix: common/null-safety/not-null-assertion 위반 수정 (Sample.kt:3, 6)

# 올바른 예
프로필 화면에서 닉네임이 없을 때 앱이 종료되지 않도록 수정

닉네임이 비어 있으면 강제 언래핑(!!)에서 NullPointerException 이 발생해
앱이 종료됐다. 닉네임이 없으면 기본 문구를 표시하도록 바꿨다.

- app/src/main/java/.../ProfileViewModel.kt

# 올바른 예 (방어용)
refactor: 홈 화면 이펙트가 최신 콜백과 문구를 사용하도록 변경

LaunchedEffect 가 시작될 때 캡처한 onAccountClick 과 오류 문구를 계속 사용하던
코드를 rememberUpdatedState 로 감쌌다. 지금은 호출하는 쪽이 항상 같은 콜백을
전달하고 문구는 설정이 변경될 때만 바뀌어 현재 동작은 바뀌지 않는다. 호출하는
쪽이 다른 콜백을 전달하도록 바뀌면 이전 콜백이 호출되는 것을 막는다.

- feature/home/src/main/kotlin/.../HomeRoute.kt
```

## 4. 리포트 작성

리뷰 결과를 입력의 `리포트 경로` 에 아래 형식으로 작성한다. `autoFix` 와 관계없이, 위반이 없어도 리포트를 작성한다.

````markdown
# kotlin-harness 리뷰 리포트

- 일시: 2026-09-27 15:30
- 범위: branch (base `main`, `a1b2c3d..e4f5g6h`)
- 시작 커밋: `e4f5g6h` / 작업 중인 파일: 없음
- platform: android (자동 판정) / 설정 파일: 없음
- 제외한 카테고리: scope-functions (없으면 `없음`)
- 대상 파일: 12개 / 적용한 룰: 34개
- 결과: error 2건, warning 5건
- 수정: 5건 수정 (커밋 3개), 2건 수정하지 않음
- 영향: 실제 문제 2건, 방어용 4건, 판정 불가 1건

## 룰별 집계

| 룰 ID | severity | 건수 |
|---|---|---|
| common/coroutines/global-scope | error | 2 |
| common/null-safety/not-null-assertion | warning | 3 |

## 위반 목록

### 1. [error] common/coroutines/global-scope

- 위치: `app/src/main/.../SyncManager.kt:42`
- 규칙: 룰 파일의 `#` 제목
- 근거: 룰의 `source` URL

```kotlin
// 위반한 코드. 앞뒤 2줄 정도를 포함한다
```

- 위반 내용: 이 코드가 룰을 위반하는 이유 한두 줄
- 영향: `실제 문제` | `방어용` | `판정 불가` — 근거 한 줄 (확인한 호출부·선언 위치 포함)
- 수정 제안:

```kotlin
// 수정한 코드
```

- 처리: `수정함 (커밋 a1b2c3d)` | `수정함 (커밋하지 않음: 이유)` | `수정하지 않음: 이유` | `autoFix 비활성화`

## 허용으로 제외한 코드

| 위치 | 룰 ID | 해당한 허용 조건 |
|---|---|---|
| `.../Foo.kt:10` | common/null-safety/not-null-assertion | 근거를 주석으로 적은 `!!` |
````

- 코드 하나가 룰 여러 개에 해당하면 룰마다 한 항목씩 보고한다. 한 번의 수정으로 모두 해소돼도 항목을 합치지 않는다. 룰의 `## 허용` 에 다른 룰로 보고한다고 적힌 경우만 그 룰로 보고한다.
- 위반 목록은 severity(`error` → `warning`), 같은 severity 안에서는 파일 경로·줄 번호 순으로 정렬한다.
- 룰에 해당하는 코드였지만 `## 허용` 에 해당해 보고하지 않은 코드는 `허용으로 제외한 코드` 에 기록한다. 없으면 이 섹션을 생략한다.

## 5. 검수 결과 반영

입력으로 검수 에이전트가 발견한 문제 목록을 받은 경우에는 1~2단계를 다시 실행하지 않는다. 리포트와 문제 목록을 읽고 아래만 처리한다.

- 누락된 위반: 3단계 기준으로 수정·커밋하고, 리포트의 위반 목록·룰별 집계·요약에 추가한다.
- 수정이 완료되지 않은 위반: 수정을 마치고 처리 결과를 갱신한다.
- 영향 판정이 틀린 항목: 리포트의 `영향` 을 고친다. 그 수정의 커밋 메시지도 고쳐야 하면, 이번 실행에서 만든 커밋이고 그 뒤에 다른 커밋이 없을 때만 `git commit --amend` 로 고친다. 그 밖의 경우는 커밋을 수정하지 않고 `반영하지 않음` 과 올바른 메시지를 적어 사용자가 판단하게 한다.
- 리포트와 실제 상태가 다른 항목: 리포트를 실제 상태에 맞게 수정한다.
- 위반과 관계없는 변경, 잘못 커밋한 파일: 되돌리지 않는다. 사용자가 판단한다.

처리한 결과를 리포트의 `## 검수 결과` 아래 `### 반영 결과` 에 문제마다 한 줄씩 적는다 (`반영함 (커밋 a1b2c3d)` | `반영하지 않음: 이유`). 반영한 내용은 다시 검수하지 않는다.

## 6. 반환

리포트 경로, 요약 수치, 생성한 커밋 목록(`해시 제목`)만 반환한다.
