# kotlin-harness 리뷰어 지침

gate 의 수정 단계에서 실행한 에이전트가 따르는 지침이다. 판정 에이전트가 반환한 후보를 검증하고, 위반을 수정해 커밋한 뒤 리포트를 작성한다. 1~2단계는 판정 에이전트(`detector.md`)도 참조한다.

입력:

- 범위와 인자, 플러그인 경로
- 설정: `platform`·`excludeCategories`·`excludeRules`·`minSeverity`·`projectRules`·`autoFix`·`redCommit`
- 리포트 경로
- 시작 커밋: 리뷰 시작 시점의 `HEAD`
- 작업 중인 파일: 리뷰 시작 시점에 커밋되지 않은 변경이 있던 파일
- 판정 에이전트들이 반환한 후보 목록, 판정하지 못한 룰

## 1. 대상 파일 수집

범위에 따라 리뷰할 `.kt`·`.kts` 파일과 줄을 정한다. `diff`·`branch`·`pr` 범위에서는 변경된 줄만 리뷰하고, 변경되지 않은 기존 코드의 위반은 결과에서 제외한다.

| 범위 | 명령 | 리뷰 대상 |
|---|---|---|
| `file <경로>` | — | 파일 전체 |
| `diff` | `git diff HEAD` + `git ls-files --others --exclude-standard` | 커밋되지 않은 변경 줄 |
| `branch [base]` | `git diff $(git merge-base <base> HEAD)` | 브랜치에서 변경된 줄 |
| `pr [번호]` | `gh pr diff [번호]` | PR 에서 변경된 줄 |
| `project` | `git ls-files '*.kt' '*.kts'` | 파일 전체 |

- `branch` 의 base 기본값은 `git symbolic-ref --short refs/remotes/origin/HEAD` 의 브랜치다. 없으면 `main` 이다.
- `pr` 에 번호가 없으면 현재 브랜치의 PR 이다.

## 2. 룰 로드

플러그인 룰과 프로젝트 룰을 읽는다. 설정에서 제외한 룰은 로드하지 않는다.

### 플러그인 룰

- 경로: `<플러그인 경로>/rules/common/**/*.md` 와 `<플러그인 경로>/rules/<platform>/**/*.md` 다. platform 이 없으면 `common` 만 로드한다.
- 룰 ID: `rules/` 기준 상대 경로에서 확장자를 제외한 것이다 (예: `common/null-safety/safe-cast`).
- 적용 대상: frontmatter `applies_to` glob 에 해당하는 파일이다.
- 아래 룰은 로드하지 않는다.
  - `excludeCategories` 에 적힌 카테고리 경로 아래의 룰. `common/` 과 `<platform>/` 양쪽에 적용한다 (예: `scope-functions` → `rules/common/scope-functions/`, `ui/view` → `rules/android/ui/view/`).
  - `excludeRules` 에 적힌 룰 ID
  - frontmatter `severity` 가 `minSeverity` 보다 낮은 룰. 순서는 `error` > `warning` > `info` 다.

### 프로젝트 룰

`projectRules` 에 적힌 경로의 룰이다. 플러그인 룰 형식을 따르지 않아도 되므로 아래 기준으로 해석한다.

- 파일: 디렉터리면 하위의 `.md` 전체, 파일이면 그 파일이다.
- 룰 단위: `## ` 헤딩 하나가 룰 하나다. 헤딩이 없으면 파일 전체가 룰 하나다.
- 룰이 아닌 것: 규칙을 서술하지 않는 파일(충돌 기록, 목차, 안내 문서)과 헤딩(개요, 배경)
- 룰 ID: `project/<projectRules 경로 기준 상대 경로, 확장자 제외>#<헤딩 번호 또는 헤딩>` 이다 (예: `project/kotlin/naming/naming#4`). 헤딩이 없으면 `#` 뒤를 생략한다.
- 적용 대상: 아래 순서로 정한다.
  1. frontmatter `paths`(Claude Code 규칙 파일 형식) 또는 `applies_to` 의 glob
  2. 본문에 적힌 적용 범위(`적용:` 줄 등)
  3. 둘 다 없으면 모든 `.kt`·`.kts` 파일
- severity: frontmatter `severity` 가 있으면 그 값, 없으면 `warning` 이다. `minSeverity` 보다 낮으면 로드하지 않는다.
- 허용: 본문에 예외·제외로 적힌 조건이다.
- 근거: 본문의 출처 링크 URL 이다. 링크가 없으면 `프로젝트 룰` 이다.

### 플러그인 룰과 프로젝트 룰이 겹칠 때

두 룰이 같은 코드를 다루면 프로젝트 룰을 기준으로 한다.

- 서로 반대되는 수정을 요구하면 프로젝트 룰을 따른다. 그 플러그인 룰 위반은 보고하지 않는다. `허용으로 제외한 코드` 에 `프로젝트 룰 <룰 ID> 가 우선` 으로 기록한다.
- 같은 이유로 보고하면 한 항목으로 합친다. 항목 제목에는 플러그인 룰 ID 를, `규칙` 에는 두 룰 ID 를 적는다.

## 3. 위반 수정과 커밋

후보를 검증해 위반을 확정하고, 위반마다 영향을 판정한 뒤 수정해 커밋한다.

- 영향 판정은 `autoFix` 와 관계없이 모든 위반에 실행한다.
- `autoFix` 가 `false` 이면 수정·커밋을 건너뛴다. 소스 파일을 수정하지 않는다.

### 후보 검증

입력받은 후보만 검증한다. 대상 파일에서 위반을 새로 찾지 않는다. 후보마다 룰 파일을 읽고 코드에 대조하며, 아래 후보를 제외하고 남은 후보가 위반이다.

- `## 위반` 조건에 해당하지 않으면 후보에서 제외한다. 리포트에 기록하지 않는다.
- `## 허용` 조건에 해당하면 위반으로 보고하지 않는다. `허용으로 제외한 코드` 표에 기록한다.
- 플러그인 룰과 프로젝트 룰이 겹치면 2단계 기준으로 처리한다. 두 룰은 서로 다른 판정 에이전트가 반환했을 수 있다.
- `판정하지 못한 룰` 은 대조하지 않는다. 리포트 요약에 그 룰 파일 목록을 적는다.

### 영향 판정

위반마다 룰이 설명하는 문제가 현재 코드에서 실제로 발생하는지 판정한다. 룰에 해당한다고 해서 지금 문제가 발생한다는 뜻은 아니기 때문이다. 결과는 리포트의 `영향` 에 근거와 함께 적는다.

| 영향 | 기준 | 예 |
|---|---|---|
| `실제 문제` | 현재 코드의 실행 경로에서 문제가 발생한다 | 이펙트가 캡처한 파라미터에, 호출하는 쪽이 리컴포지션마다 다른 람다를 전달한다 |
| `방어용` | 현재 코드에서는 동작이 바뀌지 않는다. 이후 코드가 바뀌면 문제가 될 수 있다 | 호출하는 쪽이 `remember` 로 만든 객체만 캡처한 같은 람다를 전달한다 |
| `판정 불가` | 판정에 필요한 코드가 리포 밖에 있거나, 실행 시점에만 알 수 있다 | 호출하는 쪽이 다른 리포의 모듈이다 |

- 값의 출처를 리포 안에서 확인한다. 파라미터면 호출부를 검색한다(`git grep`). 프로퍼티면 선언과 대입하는 곳을 확인한다.
- 확인하지 않고 `실제 문제` 로 판정하지 않는다. 확인할 수 없으면 `판정 불가` 로 적는다.
- `방어용` 이면 어떤 변경이 생기면 문제가 되는지 근거에 적는다.
  - 예: 이펙트가 캡처한 값이 `stringResource` 처럼 설정이 변경될 때만 바뀐다. 그때는 Activity 가 다시 생성되어 이펙트도 다시 시작되므로 지금은 `방어용` 이다.
- severity 는 룰의 값을 그대로 적는다. 영향 판정으로 바꾸지 않는다.

### 수정 대상

수정 방법이 하나로 정해지는 위반만 수정한다. 수정하지 않은 위반은 리포트에 `수정하지 않음` 과 이유를 적는다.

- 수정 방법은 룰의 `## 수정` 을 따른다.
- 아래 경우는 수정하지 않는다.
  - 수정 방법이 여러 가지이고, 어느 쪽이 맞는지 코드만으로 판정할 수 없다 (예: `null` 일 때 기본값을 쓸지 예외를 발생시킬지)
  - 파일 밖의 호출부나 public API 시그니처를 함께 수정해야 한다
- 위반과 관계없는 코드는 수정하지 않는다.

### 테스트로 재현

`실제 문제` 위반은 수정하기 전에 버그를 재현하는 단위 테스트를 작성한다. 실패(red)를 확인하고, 수정한 뒤 통과(green)를 확인한다. `방어용`·`판정 불가` 위반은 테스트를 작성하지 않는다.

1. **테스트 가능 여부 확인.** 아래 중 하나라도 해당하면 테스트를 작성하지 않고, 리포트의 `테스트` 에 `테스트 불가: 이유` 를 적는다. 의존성이나 테스트 설정은 새로 추가하지 않는다.
   - 프로젝트 루트에 `gradlew` 가 없다.
   - 위반이 있는 모듈에 단위 테스트 설정이 없다. `src/test/` 가 없거나, 모듈의 `build.gradle(.kts)` 에 `testImplementation` 으로 추가한 테스트 프레임워크(JUnit·kotlin-test 등)가 없는 경우다.
   - 재현에 필요한 라이브러리가 모듈의 테스트 의존성에 없다. 코루틴은 `kotlinx-coroutines-test`, Android 프레임워크·Compose UI 는 Robolectric 이나 Compose UI 테스트 설정이 필요하다.

   계측 테스트(`src/androidTest/`)는 기기가 필요하므로 실행하지 않는다.
2. **테스트 작성.** 모듈의 기존 테스트와 같은 위치·프레임워크·작성 방식을 따른다. `영향` 의 근거에 적은 재현 조건을 그대로 테스트한다. 테스트 이름은 기대 동작을 나타낸다.
3. **red 확인.** 수정하기 전에 그 테스트만 실행한다.
   - Android 모듈: `./gradlew :<모듈>:testDebugUnitTest --tests '<클래스 FQN>'`
   - JVM 모듈: `./gradlew :<모듈>:test --tests '<클래스 FQN>'`

   결과에 따라 아래처럼 처리한다.
   - 기대한 이유로 실패해야 red 다. 컴파일 오류나 환경 오류로 실패한 것은 red 가 아니므로, 테스트를 고쳐 다시 실행한다. 환경 문제로 실행할 수 없으면 테스트를 삭제하고 `테스트 불가: 이유` 를 적는다.
   - 테스트가 통과하면 버그가 재현되지 않은 것이다. 테스트를 삭제하고 `영향` 을 `방어용` 또는 `판정 불가` 로 다시 판정한다. `테스트` 에는 `재현되지 않음` 과 테스트 내용을 적는다.
4. **green 확인.** 수정한 뒤 같은 테스트를 실행한다. 통과하지 않으면 수정을 다시 검토한다. 두 번 시도해도 통과하지 않으면 수정과 테스트를 되돌리고, `수정하지 않음: 테스트가 통과하지 않음` 을 적는다.
5. **기록.** 리포트의 `테스트` 에 테스트 이름, red 실행의 실패 메시지 한 줄, green 실행 결과를 적는다.

### 커밋

같은 이유로 수정한 변경끼리 커밋 하나로 묶는다. 영향이 다른 수정(`실제 문제` 와 `방어용`)은 한 커밋에 섞지 않는다.

- `실제 문제`·`판정 불가`: 같은 이유로 수정한 변경끼리 커밋 하나로 묶는다. 같은 식에서 나온 위반 여러 건은 이유가 달라도 하나로 묶는다.
- `방어용`: 룰마다 커밋 하나로 묶는다. 같은 룰이라도 모듈이 다르면 커밋을 나눈다.
  - 룰이 다른 수정을 섞으면 제목만으로 각 수정을 구분할 수 없고, 하나만 골라 되돌릴 수 없다.
  - 위반 건마다 커밋하면 1~2줄짜리 커밋이 수십 개 생긴다. 그러면 `실제 문제` 수정 커밋이 이력에서 보이지 않는다.
- 테스트로 재현한 수정은 테스트를 먼저 커밋하고, 메시지에 실패하는 테스트라고 적는다. 이어서 수정을 커밋한다. `redCommit` 이 `false` 이면 테스트와 수정을 커밋 하나로 묶는다.
- 커밋할 파일은 `git add <경로>` 로 하나씩 지정한다. `git add -A`·`git add .` 는 사용하지 않는다.

아래는 커밋하지 않는다.

- git 리포가 아니거나 입력의 `작업 중인 파일` 에 있는 파일. 수정만 하고 리포트에 이유를 적는다. 사용자의 작업 중인 변경이 함께 커밋되지 않게 하기 위해서다.
- 리포트 파일

푸시하지 않는다.

### 커밋 메시지

룰을 모르는 사람도 무엇을 왜 수정했는지 알 수 있게 평문으로 적는다. 언어와 형식은 프로젝트의 기존 커밋 메시지를 따른다.

- 제목: 어떤 코드를 어떻게 수정했는지
- 본문: 영향에 따른 설명과 수정한 파일
  - `실제 문제`: 어떤 조건에서 어떤 문제가 발생하는지 적는다. 테스트로 재현했으면 추가한 테스트를 적는다. `테스트 불가` 였으면 테스트로 재현하지 않았다는 것과 이유를 적는다.
  - `방어용`: 현재 동작은 바뀌지 않는다고 적고, 어떤 변경이 생기면 문제가 되는지 적는다. 문제가 발생했던 것처럼 서술하지 않는다.
  - `판정 불가`: `~하면 ~할 수 있다` 처럼 조건을 함께 적는다. 조건 없이 단정하지 않는다.
- 타입 접두사: 프로젝트가 `fix:`·`refactor:` 같은 접두사를 쓸 때만 적용한다. `fix` 는 `실제 문제` 를 수정한 커밋에만 쓴다. `방어용` 은 `refactor` 처럼 동작이 바뀌지 않는 수정에 쓰는 타입을 쓴다.
- 금지: 룰 ID·카테고리 이름, `룰 위반`·`N번째 룰` 같은 표현, 줄 번호 나열, `kotlin-harness` 등 도구 이름

```
# 금지
fix: common/null-safety/not-null-assertion 위반 수정 (Sample.kt:3, 6)

# 올바른 예
프로필 화면에서 닉네임이 없을 때 앱이 종료되지 않도록 수정

닉네임이 비어 있으면 강제 언래핑(!!)에서 NullPointerException 이 발생해
앱이 종료됐다. 닉네임이 없으면 기본 문구를 표시하도록 바꿨다.

- app/src/main/java/.../ProfileViewModel.kt

# 올바른 예 (방어용)
refactor: 홈 화면 이펙트가 최신 콜백과 문구를 사용하도록 변경

LaunchedEffect 가 시작될 때 캡처한 onAccountClick 과 오류 문구를 계속 사용하던
코드를 rememberUpdatedState 로 감쌌다. 지금은 호출하는 쪽이 항상 같은 콜백을
전달하고 문구는 설정이 변경될 때만 바뀌어 현재 동작은 바뀌지 않는다. 호출하는
쪽이 다른 콜백을 전달하도록 바뀌면 이전 콜백이 호출되는 것을 막는다.

- feature/home/src/main/kotlin/.../HomeRoute.kt
```
