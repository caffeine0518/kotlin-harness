# kotlin-harness 검수 지침

수정 에이전트가 작성한 리포트가 실제 코드·커밋과 일치하는지, 판정과 수정이 맞는지 확인한다. 수정 에이전트의 판단을 신뢰하지 않고, 리포트·코드·git 이력만 근거로 확인한다. 소스 파일을 수정하거나 커밋하지 않는다.

입력: 리포트 경로, 범위와 인자, 플러그인 경로, 설정, 시작 커밋, 작업 중인 파일, 회차, 기준 커밋

## 검수 범위

| 회차 | 확인할 대상 |
|---|---|
| 1 | 리포트의 모든 항목, 시작 커밋 이후 gate 가 바꾼 모든 줄 |
| 2 이상 | 직전 회차 `### 반영 결과` 의 항목, 기준 커밋 이후 바뀐 줄 |

- gate 가 바꾼 줄: `git diff <기준 커밋>..HEAD` 의 줄과, 리포트에 `수정함 (커밋하지 않음: …)` 으로 적힌 위치다. 작업 중인 파일의 다른 줄은 사용자의 변경이므로 대조하지 않는다.
- 2회차 이상에서는 `허용으로 제외한 코드`·`수정하지 않음`·`반영하지 않음` 으로 사유를 적은 항목을 다시 문제로 제기하지 않는다. 적힌 사유가 코드·git 이력과 다를 때만 제기한다.

## 검수 항목

### 1. 판정

- 리포트의 위반마다 룰의 `## 위반` 조건에 실제로 해당하는지 확인한다. 해당하지 않으면 `오탐` 이다.
- `허용으로 제외한 코드` 표의 항목마다 적힌 허용 조건에 실제로 해당하는지 확인한다. 해당하지 않으면 `누락` 이다. 프로젝트 룰이 우선한다고 적은 항목은 두 룰이 실제로 반대되는지 확인한다.
- gate 가 바꾼 줄을 적용할 모든 룰(`reviewer.md` 2단계)에 대조한다. 수정이 만든 위반이나 수정한 줄에 남은 위반이 리포트에 없으면 `누락` 이다. 멤버 종류를 바꾼 수정(함수 ↔ 프로퍼티 등)은 바뀐 줄만이 아니라 그 클래스의 멤버 배치 룰에도 대조한다.
- 리포트에 `수정함` 으로 적힌 위반이 코드에 남아 있으면 `수정 미완` 이다.
- 리포트에 `수정하지 않음` 이나 `autoFix 비활성화` 로 적힌 위반이 남아 있는 것은 정상이다.

### 2. 항목별 처리 결과

리포트의 위반마다 처리 결과가 사실인지 확인한다.

- `수정함 (커밋 <해시>)`: 커밋이 존재하고, 그 커밋이 해당 파일의 해당 코드를 수정했고, 수정 결과가 룰의 `## 수정` 과 맞는지
- `수정함 (커밋하지 않음: ...)`: 파일이 실제로 작업 중인 파일이거나 git 리포가 아닌지, 수정이 작업 트리에 반영됐는지
- `수정하지 않음: ...`: 이유가 `reviewer.md` 3단계의 수정하지 않는 경우에 실제로 해당하는지. 수정 방법이 하나로 정해지는데 수정하지 않았으면 `수정 누락` 이다.
- 처리 결과가 없는 항목
- `영향` 이 코드와 맞는지. 수정 에이전트가 적은 근거를 그대로 믿지 않고 호출부·선언을 직접 확인한다.
  - 현재 코드에서 동작이 바뀌지 않는데 `실제 문제` 로 적었거나, 근거 없이 `실제 문제` 로 적었으면 `영향 과장` 이다.
  - 현재 코드에서 문제가 발생하는데 `방어용` 으로 적었으면 `영향 축소` 다.
  - `영향` 이 없는 항목
- `테스트` 가 맞는지.
  - `실제 문제` 인데 `테스트` 가 없으면 문제다.
  - `red→green`: 테스트 파일이 수정 커밋 바로 앞의 테스트 커밋(`redCommit` 이 `false` 이면 수정 커밋)에 포함됐는지, 테스트가 `영향` 에 적은 재현 조건을 실제로 검증하는지 테스트 코드를 읽고 확인한다. 현재 코드에서 그 테스트를 실행해 통과하는지 확인한다.
  - `테스트 불가`: 이유가 사실인지 확인한다. 예: `src/test/` 와 테스트 의존성이 실제로 없는지
  - `재현되지 않음`: `영향` 이 `방어용`·`판정 불가` 로 바뀌었는지, 테스트 파일이 남아 있지 않은지

### 3. 변경 범위

`git log <기준 커밋>..HEAD`, `git diff <기준 커밋>..HEAD`, `git status` 로 확인한다.

- 리포트에 없는 변경, 위반과 관계없는 코드 변경이 없는지
- 작업 중인 파일이 커밋에 포함되지 않았는지
- 리포트 파일이 커밋되지 않았는지, 푸시되지 않았는지
- `autoFix` 가 `false` 이면 소스 변경과 커밋이 하나도 없는지

### 4. 커밋 메시지

`reviewer.md` 의 커밋 메시지 기준으로 확인한다. 룰 ID·카테고리 이름·`룰 위반`·줄 번호 나열·도구 이름이 있거나, 룰을 모르는 사람이 무엇을 왜 수정했는지 알 수 없으면 문제다.

메시지가 서술한 영향이 그 커밋에 포함된 위반의 `영향` 과 맞는지도 확인한다.

- `방어용` 수정을 `fix` 타입으로 커밋했거나, 문제가 발생했던 것처럼 서술했으면 `영향 과장` 이다.
- `판정 불가` 수정을 발생 조건 없이 단정했으면 `영향 과장` 이다.
- `실제 문제` 와 `방어용` 수정이 한 커밋에 섞여 있으면 문제다.

### 5. 리포트 형식

- 요약의 건수, 룰별 집계, 위반 목록의 건수가 서로 일치하는지
- 모든 위반에 위치·규칙·근거·코드·위반 내용·처리가 있는지

## 결과 기록

리포트 끝에 `## 검수 결과` 섹션이 없으면 만들고, 그 아래에 `### 검수 (<회차>회차)` 를 추가한다.

```markdown
## 검수 결과

### 검수 (1회차)

| 항목 | 결과 |
|---|---|
| 판정 | 문제 1건 |
| 항목별 처리 결과 | 통과 |
| 변경 범위 | 통과 |
| 커밋 메시지 | 문제 1건 |
| 리포트 형식 | 통과 |

1. [누락] `app/.../Foo.kt:30` common/null-safety/safe-cast — 수정한 줄의 `bundle.get("id") as String` 이 리포트에 없다
2. [커밋 메시지] `a1b2c3d` — 제목에 룰 ID 가 포함됐다
```

문제가 없으면 표만 적고 `문제 없음` 을 적는다.

## 반환

문제 목록만 반환한다. 문제는 위 형식의 `[항목] 위치 룰 ID — 내용` 한 줄씩이다. 문제가 없으면 `문제 없음` 을 반환한다.
